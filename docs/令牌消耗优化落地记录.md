## 1. 文档目的

`token-engineering-checklist.md` 记录的是改造计划，`token-engineering-evaluation.md` 记录的是评测结果。  
这份文档补充的是两者之间缺失的内容：**本轮最终实际落地了哪些令牌消耗优化、分别改在什么位置、解决了什么问题、当前还剩哪些未完成项。**

## 2. 本轮最终已落地的优化点

### 2.1 统一 LLM 调用埋点，先把 token 花在哪看清楚

落地位置：

- `backend/app/tools/llm_client.py`
- `backend/app/services/chat_service.py`
- `backend/app/services/flow_trace_service.py`

实际改动：

- 新增 `invoke_with_metrics` 和 `astream_with_metrics`，统一包裹同步 / 流式 LLM 调用
- 每次调用记录 `node_name`、`model`、`prompt_tokens`、`completion_tokens`、`latency_ms`、`success`
- 在聊天主链路补齐结构化 trace，额外记录 `rag_used`、`web_used`、`cache_hit`、`summary_used`
- 最终把关键结果写入 `docs/flow-trace-record.md` 和 `docs/flow-trace-record.jsonl`

解决的问题：

- 改造前很难判断 token 是消耗在最终回答、RAG 证据、还是轻量路由节点
- 改造后可以按节点看 prompt 体积和耗时，后续优化不再靠感觉

说明：

- 这一项本身不是直接“省 token”，但它是后续预算压缩、缓存、摘要能否验证收益的前提

### 2.2 引入 Executor 上下文预算器，替代单纯堆上下文

落地位置：

- `backend/app/services/token_budget_service.py`
- `backend/app/agents/executor.py`
- `backend/app/core/config.py`

实际改动：

- 新增 `estimate_tokens`、`truncate_text_to_budget`、`allocate_context_budgets`、`compress_context_sections`
- 最终回答 prompt 改成按区块做预算分配，而不是简单按“最近几条历史 + 前几个 chunk”拼接
- 当前默认预算配置：
  - `EXECUTOR_PROMPT_MAX_TOKENS=2600`
  - `EXECUTOR_COMPLETION_RESERVE_TOKENS=600`
  - `TOKEN_BUDGET_PROFILE_TOKENS=180`
  - `TOKEN_BUDGET_SUMMARY_TOKENS=220`
  - `TOKEN_BUDGET_RECENT_HISTORY_TOKENS=360`
  - `TOKEN_BUDGET_RAG_TOKENS=900`
  - `TOKEN_BUDGET_WEB_TOKENS=320`
- 预算区块覆盖：
  - `user_profile`
  - `conversation_summary`
  - `conversation_history`
  - `retrieved_evidence`
  - `web_evidence`

解决的问题：

- 长会话、长画像、长 RAG 证据同时存在时，prompt 会快速膨胀
- 过去更像“字符级截断”，现在变成“预算驱动压缩”，至少能保证每类上下文都在受控范围内
- completion 预留被单独留出，降低 prompt 挤爆模型上限的风险

最终效果：

- 在评测场景中，最终回答 prompt 从 `10213` tokens 降到 `1858` tokens
- 降幅 `81.81%`

### 2.3 引入滚动会话摘要，避免只保留最近消息导致上下文断层

落地位置：

- `backend/app/services/session_summary_service.py`
- `backend/app/agents/memory.py`
- `backend/app/core/state.py`

实际改动：

- 在状态里增加：
  - `conversation_summary`
  - `summary_signature`
  - `summary_source`
  - `summary_updated_at`
  - `summary_used`
- 当历史超过 `HISTORY_HARD_LIMIT=20` 时，不再只保留最近消息
- 旧消息会先被整理成滚动摘要，再把最近 20 条原始对话保留下来
- 当前默认摘要策略是启发式压缩；`SESSION_SUMMARY_USE_LLM=false` 时不会额外引入摘要模型成本
- 如果后续打开 `SESSION_SUMMARY_USE_LLM`，可切到轻量模型生成更高质量摘要

解决的问题：

- 纯裁剪历史虽然能省 token，但容易丢失病程、已给建议、用户偏好等关键信息
- 滚动摘要把“旧信息保留”与“上下文缩小”这两个目标兼容起来

最终效果：

- 长历史被压缩后，旧轮次信息仍能通过 `conversation_summary` 进入最终 prompt
- 长上下文压缩收益不再完全依赖生硬截断

### 2.4 RAG 证据从“按条数塞进去”改成“按 token 额度压缩”

落地位置：

- `backend/app/services/token_budget_service.py`
- `backend/app/agents/executor.py`

实际改动：

- RAG 证据进入最终回答前，改走 `render_evidence_text`
- 每段证据先做单段 token 裁剪，再受总预算限制
- 当前默认行为：
  - 单段证据默认按 `180` tokens 压缩
  - 最多保留 `6` 段进入最终 prompt
  - 总体受 `TOKEN_BUDGET_RAG_TOKENS=900` 控制
- Executor 只消费压缩后的证据，而不是把检索结果原样堆进 prompt

解决的问题：

- 之前 RAG chunk 一长，最终 prompt 会被证据区块快速撑大
- 现在 RAG 消耗被限制在稳定区间，证据仍保留，但不会挤占掉整个回答上下文

说明：

- 本轮完成的是**进入 Executor 前的证据压缩**
- 检索召回阶段仍是 `固定 k + rerank`，还没有升级成真正的预算驱动检索

### 2.5 对高重复、低风险节点做进程内 TTL 缓存

落地位置：

- `backend/app/services/cache_service.py`
- `backend/app/agents/judge_need_rag.py`
- `backend/app/agents/medical_router.py`
- `backend/app/agents/query_rewriter.py`
- `backend/app/agents/retriever.py`

实际改动：

- 新增进程内 TTL 缓存，默认 `CACHE_TTL_SECONDS=600`
- 当前已接入缓存的节点：
  - `judge_need_rag`
  - `medical_router`
  - `query_rewriter`
  - `retriever`
- 缓存键包含必要上下文，例如 `tenant_id`、`user_id`、`question`、`domain`、`scope`、`department`
- 命中 / 未命中会写入：
  - `state["cache_stats"]`
  - `state["node_metrics"][node]["cache_hit"]`

解决的问题：

- 很多轻量链路节点虽然单次 token 不高，但重复问题会被反复调用
- 对完全重复或高重复请求，这类 prompt 消耗可以直接归零

最终效果：

- 在评测链路中，`medical_router + query_rewriter` 首次请求消耗 `343` prompt tokens
- 缓存命中后重复请求降为 `0` prompt tokens
- 降幅 `100%`

### 2.6 增加开关与回滚位，避免多项优化绑死上线

落地位置：

- `backend/app/core/config.py`
- `backend/.env.example`

实际改动：

- 已接入的主要开关：
  - `TOKEN_BUDGET_ENABLED`
  - `SESSION_SUMMARY_ENABLED`
  - `SESSION_SUMMARY_USE_LLM`
  - `CACHE_ENABLED`

解决的问题：

- 预算器、摘要、缓存都属于行为层改造，如果没有开关，出现回归时只能整包回退
- 现在可以按能力逐项启停，便于灰度和问题定位

### 2.7 为 token 工程改造补了回归测试门禁

落地位置：

- `backend/tests/test_token_engineering_upgrade.py`
- `backend/tests/test_deepeval_contracts.py`
- 以及新增的一组 contract / retrieval / routing 测试文件

实际改动：

- 覆盖了以下关键行为：
  - 长历史会生成滚动摘要
  - Executor 会记录预算并使用 `conversation_summary`
  - 重复请求会命中缓存
  - 长上下文场景下优化版 prompt 明显小于旧版 prompt
- 评估记录显示：
  - token 工程专项测试 `4 passed`
  - 后端全量测试 `133 passed`

解决的问题：

- token 优化最容易出现“省了 token，但回复契约坏了”
- 现在至少对摘要、预算、缓存三条主线有自动化回归保护

## 3. 本轮优化后的实际收益汇总

### 3.1 单次长上下文请求压缩

- 评测日期：2026-03-21
- 场景：`28` 条长多轮历史、`8` 个长 RAG chunk、带长期画像、不触发联网搜索
- 结果：
  - 改造前：`10213` tokens
  - 改造后：`1858` tokens
  - 降幅：`81.81%`

收益来源判断：

- 主要收益来自 `recent history` 和 `RAG evidence` 的预算压缩
- 滚动摘要负责把被裁掉的旧信息重新浓缩回 prompt

### 3.2 重复请求链路压缩

- 评测日期：2026-03-21
- 场景：重复执行 `medical_router`、`query_rewriter`
- 结果：
  - 首次请求：`343` prompt tokens
  - 缓存命中后：`0` prompt tokens
  - 降幅：`100%`

收益来源判断：

- 这部分不是“单次请求更短”，而是“重复流量不再重复花 token”

## 5. 当前没有完成的部分

以下内容仍应归类为“下一阶段”，不应写成本轮已完成：

1. **预算驱动检索还没做完**
   当前只是把检索结果在进入 Executor 前压缩；Retriever 召回仍是固定 `k + rerank`。

2. **前端渐进式披露还没落地**
   还没有默认“简要回答 / 展开详情”的两段式请求与展示。

3. **摘要 LLM 模式默认未开启**
   `SESSION_SUMMARY_USE_LLM=false`，说明现在优先追求低成本和稳定性，摘要质量上限仍可继续提升。

4. **线上持续观测还需要补**
   目前文档里有本地评测结果，但真实线上流量的 `平均 prompt tokens / p95 latency / cache hit rate` 还需要持续采集。

## 6. 一句话结论

本轮 token 工程改造已经把“最终回答 prompt 过大”和“重复轻量节点反复耗 token”这两个主要问题处理掉了：  
**单次长上下文请求主要靠预算器 + 摘要 + RAG 压缩来降耗，重复请求主要靠 TTL 缓存来降耗。**  
当前最值得继续推进的方向，是把 Retriever 召回阶段也改成预算驱动，并补上前端的渐进式披露。
